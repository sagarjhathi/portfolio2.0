01. Overview

The suite searches amazon.in for “Mobile”, applies each filter option in the left navigation, then checks that the products shown match the filter. It runs against the live site, either locally or on GitHub Actions. There are 8 tests:

  • Brand filter. For each brand, every product title must contain the brand name or a known alias, for example “Moto” for Motorola.
  • Specification filters. For storage, battery, discount, display size, display type, camera resolution and processor speed, the test opens the first products in separate tabs and checks the title, key features and technical details against the filter value.
8tests covering brand and seven specification filters
4 × 2CI shards times workers, so 8 tests can run side by side
2automatic retries on CI before a test is reported as failed
3CI jobs: type-check, sharded tests, merged reports

02. What makes it special

Assertions

Every mismatch in one run

Tests use expect.soft, so a run reports all the mismatches it finds instead of stopping at the first one.

Readability

Tests read like a checklist

Flows handle the multi-step work across pages and tabs and hand back plain results. The test itself is a few readable lines that loop and assert.

Resilience

Built for a live, unreliable site

It moves past Amazon’s “Continue shopping” page, reloads on a “Service Unavailable” page, and logs the URL and title when a page does not load. It does not try to solve any challenge.

Honesty

Skips instead of guessing

If a filter is missing from the navigation, the test is skipped with a reason, so a run of skips points at the site rather than silently passing.

CI

Sharded and merged

CI splits the tests into 4 parallel shards with 2 workers each, then merges the shard results into one Playwright report and one Allure report.

Config

Two run sizes

A standard run covers the first 5 filter options with 3 products each. The daily run goes wider: all options, 5 products each. Environment variables can override both.

Quality gate

Type-check before tests

A separate job runs lint and the TypeScript compiler first, so type errors fail fast before any browser starts.

Comparison

A fair side-by-side

Same scenarios, same site, different stack. It shows how Playwright’s auto-waiting and built-in parallel runner change the amount of code needed.

03. Architecture

Each layer calls only the layer below it.

  1. testsWhat is verified, in a few readable lines (AmazonAll.spec.ts).
  2. flowsMulti-step journeys across pages and tabs. They return plain results.
  3. pagesLocators and single-page actions: AmazonLandingPage and ProductListingPage.
  4. utilsRun sizing (RunConfig), screenshots, 503 recovery and the “Continue shopping” handler.

04. CI pipeline

Older push and pull request runs on the same branch are cancelled, while scheduled and manual runs are never cancelled.

  1. 1 · Trigger

    Push or pull request to master, daily at 20:00 UTC, or a manual run.

  2. 2 · Typecheck

    Lint and the TypeScript compiler run once, before any browser starts.

  3. 3 · Test

    4 parallel shards, 2 workers each, up to 2 retries. Each shard uploads a blob report and Allure results.

    shard 1/4shard 2/4shard 3/4shard 4/4

  4. 4 · Merge reports

    Shard results become one Playwright HTML report and one Allure report.

  5. 5 · Publish

    Pushes to master, scheduled and manual runs deploy to GitHub Pages. Pull requests only build.

CI keeps no traces, because they made reports very large. A failed test keeps its video and a failure screenshot. Locally, failures also keep a full trace.
