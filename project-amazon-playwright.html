Amazon Filter Automation
Playwright + TypeScript

The same Amazon filter checks as my Java project, rebuilt from scratch with Playwright and TypeScript. Building it twice let me compare the two stacks on the same problem, and see what each one does better.

01. What it does

The suite searches amazon.in for “Mobile”, applies each filter option in the left navigation, then checks that the products shown match the filter. It runs against the live site, either locally or on GitHub Actions. There are 8 tests in total:

  • Brand filter. For each brand, every product title must contain the brand name or a known alias, for example “Moto” for Motorola.
  • Specification filters. For storage, battery, discount, screen size, display type, camera resolution and processor speed, the test opens the first products in separate tabs and checks the title, key features and technical details against the filter value.

02. What makes it different

Every mismatch in one run

Tests use soft assertions, so a run reports all mismatches it finds instead of stopping at the first one.

Tests read like a checklist

Flows handle the multi-step work across pages and tabs and hand back plain results. The test itself is a few readable lines that loop and assert.

Built for a live, unreliable site

It moves past Amazon’s “Continue shopping” page, reloads on a “Service Unavailable” page, skips products with no data, and logs the URL and title when a page does not load. It does not try to solve any challenge.

Sharded CI

CI splits the tests into 4 parallel shards with 2 workers each and 2 retries, then merges the shard results into one HTML report.

Adjustable run size

A small config file picks how many filter options and products each run covers. A push runs 5 options with 3 products each, and the weekly run uses 3 options with 5 products.

A fair comparison

Same scenarios, same site, different stack. It shows how Playwright’s auto-waiting and built-in parallel runner change the amount of code needed.

03. Architecture

Each layer calls only the layer below it.

  1. testsWhat is verified, in a few readable lines (AmazonAll.spec.ts).
  2. flowsMulti-step journeys across pages and tabs. They return plain results.
  3. pagesLocators and single-page actions: AmazonLandingPage and ProductListingPage.
  4. utilsRun sizing, screenshots, 503 recovery and the “Continue shopping” handler.

04. How CI works

  1. Runs on push, pull request, a weekly schedule (Sundays 21:00 UTC) or manually
  2. typecheck job runs the TypeScript compiler once
  3. test job runs 4 parallel shards, 2 workers each, 2 retries
  4. merge-reports job combines shard reports into one HTML report

CI keeps no traces, because they made reports very large. A failed test keeps its video and a failure screenshot. Locally, failures also keep a full trace.

06. Known limitations

Being clear about what it does not do is part of the project.

  • The site can block automation. Amazon sometimes shows a “rush hour” or “Continue shopping” page, especially from CI servers, so a run can fail for reasons unrelated to a filter bug.
  • The specification check is literal. It looks for the filter text in the product text, so range filters such as “Up to 2,999 mAh” are reported as mismatches. A numeric comparison is planned.
  • A missing filter passes with a warning. If a filter does not appear, the test logs a warning and returns, so a suspiciously fast run is worth checking.
  • Locators depend on Amazon’s markup, which can change at any time, and results come from live data, so coverage is a sample.

07. Run it yourself

npm ci
npx playwright install chromium

npx playwright test              # all tests
npx playwright test --headed     # watch the browser
npx playwright show-report       # open the last report
