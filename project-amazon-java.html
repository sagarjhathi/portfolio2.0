01. Overview

The framework searches for a product category, opens the listing page and applies filter combinations from a configuration file. After each filter it collects the product list, opens the product pages, and validates their details against the filter that was applied.

It covers 11 filter areas: storage, battery, processor, discount, brands, display size, display type, camera, delivery options, the price slider and operating system. Every step is logged and every important action is captured in a screenshot, so a failed run can be understood without re-running it.

02. What makes it special

Design

Layered, like a product

Tests, flows, pages, a reliability layer and utilities each have one job. Adding a new filter means adding a flow, not rewriting tests.

Reliability

SafeActions layer

A custom wrapper around Selenium that adds waits, retries for stale or unavailable elements, automatic screenshots and consistent logging in one place. Tests stay short and stable.

Speed

Parallel and isolated

Each test gets its own WebDriver through ThreadLocal, so tests run in parallel without interfering with each other.

CI

Adaptive test depth

A code push runs a small, fast sample. The nightly CRON run tests every filter and every product. The pipeline decides this by itself, with no manual switches.

Evidence

One folder per run

Every run writes to its own timestamped folder with reports, a log file per test and screenshots grouped by test, so output from parallel tests never mixes.

Delivery

Results reach people

Extent reports and a merged Allure report go to GitHub Pages. Discord messages announce each run start and finish with links to the report and artifacts.

Resilience

Reports publish even after failures

The publish job runs even when some shards fail, so the failing run is the one with a report to read, not the one without.

Data

Data-driven and configurable

Test data lives in an Excel file read with Apache POI. Run depth, browser and headless mode come from a central properties file and Maven flags.

03. Architecture

Each layer only talks to the layer below it, so a change in one place stays in that place.

  1. Test layerAmazonTests and TestNG data providers decide what is verified.
  2. Flow layerShared and specialised flows for brand, discount, operating system, delivery and price.
  3. Page layerAmazonLandingPage and ProductListingPage hold locators and single-page actions.
  4. SafeActions layerStable click, type, scroll and lookup with retries, waits and screenshots.
  5. Driver & utilitiesDriverManager, ConfigManager, WaitUtility, GenericUtility and ExcelReader.
  6. Reporting & loggingExtentReports, Allure and Log4j2 produce the per-run artifacts.

04. CI pipeline

One GitHub Actions workflow takes a trigger all the way to a published report and a chat message.

  1. 1 · Trigger

    Push, pull request, nightly CRON or a manual run.

  2. 2 · Choose depth

    Pushes use a reduced filter and product count. The nightly run goes full depth.

  3. 3 · Parallel shards

    One runner per TestNG group, each uploading logs, screenshots and reports.

    BatteryProcessorStorageBrandsScreenSizeTypeCamEtcDeliveryPriceOs

  4. 4 · Publish

    Merges Allure results, builds a hub page with the Extent reports and deploys to GitHub Pages.

  5. 5 · Notify

    Discord messages for run start and finish, with report links.
