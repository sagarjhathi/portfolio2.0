Amazon Filter Automation
Java + Selenium

A test framework that checks whether Amazon’s search filters really work. It applies a filter, opens the real products, and confirms that each product matches what was selected. I built it like a small software product, not a pile of scripts.

01. What it does

The framework searches for a product category, opens the listing page and applies filter combinations from a configuration file. It covers filters such as brand, discount range, operating system, delivery options, price slider, battery capacity and display attributes. After each filter it collects the product list, opens the product pages, and validates their details.

Every step is logged and every important action is captured in a screenshot, so a failed run can be understood without re-running it.

02. What makes it different

Layered, like a product

Tests, flows, pages, a reliability layer and utilities each have one job. Adding a new filter means adding a flow, not rewriting tests.

SafeActions reliability layer

A custom wrapper around Selenium that adds waits, retries for stale elements, automatic screenshots and consistent logging in one place. Tests stay short and stable.

Parallel and isolated

Each test gets its own WebDriver through ThreadLocal, so tests run in parallel without interfering. Every run writes to its own timestamped folder of logs and screenshots.

CI that adapts

A code push runs a small, fast sample. The nightly CRON run tests every filter and every product. The pipeline decides this by itself, with no manual switches.

Results reach people

The Extent report is published to GitHub Pages, and Discord messages announce each run start and finish with direct links to the report and artifacts.

Data-driven and configurable

Test data lives in an Excel file read with Apache POI. Run depth, browser and headless mode come from a central properties file and Maven flags.

03. Architecture

Each layer only talks to the layer below it.

  1. Test layerAmazonTests and TestNG data providers decide what is verified.
  2. Flow layerShared and specialised flows for brand, discount, operating system, delivery and price.
  3. Page layerAmazonLandingPage and ProductListingPage hold locators and single-page actions.
  4. SafeActions layerStable click, type, scroll and lookup with retries, waits and screenshots.
  5. Driver & utilitiesDriverManager, ConfigManager, WaitUtility, GenericUtility and ExcelReader.
  6. Reporting & loggingExtentReports and Log4j2 produce the per-run artifacts.

04. How a run works

  1. Trigger: push, nightly CRON or manual run
  2. Read the configuration to decide how deep to test
  3. Start the browser and open the listing page
  4. Find the available filters and apply them one by one
  5. Collect the updated product list for each filter
  6. Open product pages and validate their attributes
  7. Save logs and screenshots for every stage
  8. Publish the report to GitHub Pages and notify Discord

06. Engineering decisions

  • TestNG over JUnit. Better support for parallel runs, data providers, listeners and retries, which a UI suite needs.
  • ExtentReports over Allure. One self-contained HTML report with screenshots and logs inside, and no extra build step.
  • Log4j2 routing. Logs go to a folder per run and a file per test, so output from parallel tests never mixes.
  • GitHub Pages for reports. Anyone can open the latest report with one click from Discord or the CI page.
  • Discord instead of email. Alerts show up where people already are and link straight to results.

07. Run it yourself

# quick smoke run
mvn clean test -DrunForAllFilterOptions=false -DoverideFilteOptionsCount=2

# full regression
mvn clean test -DrunForAllFilterOptions=true -DrunForAllProductsUnderListing=true
